# TDD·테스트 변경·사용자 흐름 관리

검토일: 2026-10-20. 기능 구현의 기본 과정과 별도 `sharp-frames-test` 명령에 반영한 기준입니다.

## 불편했던 문제와 바꾼 행동

| 문제 | 적용한 기준 | 검토할 근거 |
| --- | --- | --- |
| 실패하자 기대값을 바꿔 통과 | 실패 원인을 먼저 분류. 기대값 변경은 요구 변경·입증된 테스트 결함·의미가 같은 테스트 리팩터링에 근거 | 전후 기대값, 계약 출처, 대체 검증 |
| 새 함수에 맞춘 유닛 검사만 추가 | 구현 전에 관련 계약·주변 보존 동작·권한·상태·예외를 분석 | 요구와 케이스의 연결, 놓친 위험 |
| 개별 함수는 통과하지만 실제 사용은 실패 | 실제 역할별 연속 행동과 후속 조회·저장 상태·금지된 부작용 확인 | 경계를 통과하는 워크플로 검사와 공백 |
| 테스트가 있는데 실행하지 않음 | 계획·작성·통과·실패·skip·실행 불가를 구분 | 실행 명령, 코드 기준, 환경, 실제 결과 |
| 새 테스트로 기존 검증을 대체해 개수만 증가 | 수집된 케이스·기대값·설정·삭제·skip의 변화를 함께 검토 | 남은 의무와 제거된 의무의 대응 |

테스트 기대값이 언제나 옳다고 가정하지 않습니다. 잘못된 테스트는 고칠 수 있지만,
“현재 코드가 이렇게 반환한다”는 사실만으로 요구한 동작을 바꾸지는 않습니다. 중요한
정책이 미정이면 질문하거나 미정으로 남겨야 하며 임의의 정답을 테스트에 박아 넣지 않습니다.

## 기능 개발의 기본 순서

1. **케이스 분석:** 요구·기존 계약에서 성공과 보존 동작, 관련 경계·예외·역할·상태를 정합니다.
2. **Red:** 다음 작은 동작을 검사하는 테스트를 먼저 실행하고 의도한 이유로 실패하는지 확인합니다.
3. **Green:** 그 동작을 구현하고 같은 검사와 관련 회귀가 통과하는지 확인합니다.
4. **Refactor:** 중복과 구조를 정리하며 계약을 유지합니다.
5. **연결 검증:** 통합 경계와 핵심 사용자 흐름에서 응답·최종 상태·금지된 효과를 확인합니다.

실행 파일·패키지·환경 문제로 시작하지 못한 것은 기능 결함 재현이 아닙니다. 새 인터페이스가
없어서 실패하는 경우도 연결 후 실제 행동을 검증하는 assertion이 있어야 합니다. 실행이
막혔다면 그 단계가 막혔다고 보고하고 TDD를 수행했다고 포장하지 않습니다.

이미 요구를 만족하는 테스트가 있다면 활용합니다. 동작 보존 리팩터링은 기존 테스트를
통과하는 상태로 시작할 수 있습니다. 문구·주석 등 작은 외형 수정에 새 테스트를 강제하지
않으며, 구현 뒤 테스트를 작성했다면 실제 순서를 그대로 보고합니다.

## 유닛·통합·워크플로의 역할

유닛 테스트는 정책과 계산의 경계값을 빠르게 확인합니다. 통합 테스트는 실제 라우트·DB·
어댑터 연결의 계약을 확인합니다. 워크플로 테스트는 사용자의 목적이 여러 행동을 거쳐
달성되는지 확인합니다. 각 수준이 잡아야 할 실패를 기준으로 조합하며 비율을 고정하지 않습니다.

예를 들어 문서 공유 기능에서는 실제 제품에 존재하는 소유자·편집자·열람자를 구분합니다.
“소유자가 공유 → 편집자가 수정 → 열람자가 변경 내용을 조회”라는 연결과,
“열람자의 수정 거부 → 문서 원본 유지 → 정상 조회 가능”을 확인할 수 있습니다.
이것은 설명용 예시이며 각 프로젝트의 역할이나 권한 규칙을 대신하는 계약은 아닙니다.

백엔드라면 격리 DB를 사용하는 연속 API 요청으로 흐름을 확인할 수 있습니다. UI를 바꾸면
실제 화면 조작도 필요합니다. API 검사가 통과해도 버튼·로그인 전환·로딩/오류 화면이
작동한다고 할 수는 없습니다. 권한이나 내부 저장을 검증하면서 그 부분을 성공 mock으로
바꿔 버리면 검증 범위를 잃습니다. 외부 결제 등 대역으로 대신한 경계는 한계를 표시합니다.

모든 예외를 무작정 나열하지 않습니다. 입력 종류·동등 분할·경계값과 실제 상태 전이에서
위험한 조합을 선택합니다. 중복·재시도·부분 실패·오래된 상태·동시 요청은 관련 흐름에
적용하고, 모든 역할×상태×입력의 조합을 의무화하지 않습니다.

## 케이스 관리

기존 테스트 문서와 케이스 ID를 우선 사용합니다. 복잡한 기능에 기존 관례가 없다면
`tests/CASE_MATRIX.md`에 기능별로 모읍니다. 실행마다 새 문서를 양산하지 않습니다.
작은 변경은 안정적인 테스트 이름과 작업 보고로 충분합니다.

| 항목 | 기록 내용 |
| --- | --- |
| 케이스 ID 또는 테스트 이름 | 바뀌지 않는 식별자와 실제 테스트 위치 |
| 요구 근거 | 사용자 요구·정책·공개 계약의 출처 |
| 역할·사전 상태 | 실제 권한·소유권·준비 조건 |
| 행동·입력 | 개별 입력 또는 연속 행동 |
| 기대 결과 | 응답과 후속 조회·저장 상태·일어나면 안 되는 효과 |
| 검증 수준·공백 | 유닛·통합·API 흐름·브라우저 흐름, 대역과 미검증 경계 |

케이스 정의와 실행 결과를 분리합니다. 실행 결과에는 명령·코드 기준·환경과 통과/실패/
skip/실행 불가를 남겨 과거 통과를 현재 결과로 오해하지 않게 합니다. 요구 변경으로 케이스를
교체하면 기존 의무와 대체 케이스, 변경 이유를 연결합니다. 담당자나 기한을 임의로 만들지 않습니다.

## 테스트가 바뀌었을 때

기대값뿐 아니라 fixture·스냅샷·mock·허용 오차·재시도·skip/xfail·수집 설정·CI 선택도
확인합니다. 테스트 파일은 그대로인데 수집에서 제외된 경우도 검증 축소입니다. 무조건
모든 테스트를 불변으로 만들거나 수정 때마다 승인받게 하는 절차는 넣지 않았습니다.

정당한 변경에는 바뀐 기대나 의무, 요구 변경 또는 테스트 결함의 근거, 대체 검증을 남깁니다.
실패 후 재시도 통과도 첫 실패를 없애지는 않습니다. 격리하는 flaky 검사는 이유·공백·재검토
조건을 남기고, skip을 정상 통과로 세지 않습니다.

**스킬 지침만으로 변조를 강제로 차단할 수는 없습니다.** 구현 작성자에게 테스트와 CI의
수정 권한이 모두 있으면 지침을 어길 수 있습니다. 더 강한 보장은 작성자가 수정할 수 없는
수용 검사, 독립 검토와 실제로 적용된 CI·브랜치 보호에서 옵니다. 같은 쓰기 영역의 해시
파일도 함께 바꿀 수 있으므로 그것만으로 독립성을 주장하지 않습니다. 이 패키지가 보호
설정을 자동 설치하거나 플랫폼 권한을 바꾸지는 않습니다.

## 호출 예시

```text
$sharp-frames-development 문서 공유 기능을 추가하고 TDD로 검증해줘.
기존 권한 정책을 활용하고 역할별 연속 행동과 저장 상태까지 확인해줘.

$sharp-frames-test 이번 변경의 예외·역할·상태 케이스와 사용자 흐름을 설계만 해줘.

$sharp-frames-test 설계한 테스트와 케이스 기록을 추가해줘.
제품 코드는 고치지 말고 실패 원인과 검증 공백을 알려줘.

$sharp-frames-review 기대값·skip·mock·수집 설정 변경에 근거가 있는지 함께 검토해줘.
```

## 참고한 원저자 자료

[Martin Fowler의 TDD 설명](https://martinfowler.com/bliki/TestDrivenDevelopment.html)은
케이스 목록을 만든 뒤 red/green/refactor를 반복하는 과정을 설명합니다. 테스트를 먼저
쓰는 순서뿐 아니라 요구와 인터페이스를 생각하고 구조를 정리하는 단계까지 반영했습니다.

[Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)는
큰 E2E에 과도하게 의존할 때 피드백 속도·신뢰성·원인 격리가 어려워지는 경험을 설명합니다.
사용자 흐름을 보강하면서도 모든 예외를 비싼 E2E로 옮기지 않는 기준으로 참고했습니다.

[Playwright 권장 방식](https://playwright.dev/docs/best-practices)은 사용자에게 보이는 행동과
테스트 격리 등을 다룹니다. 특정 도구를 강제하지 않고 실제 UI를 검증할 때 적용할 기준입니다.
[pytest skip/xfail 문서](https://docs.pytest.org/en/stable/how-to/skipping.html)는 상태의 의미가
서로 다름을 확인할 자료입니다. 사용하는 러너의 실제 수집·결과를 읽어야 합니다.

이는 설계 근거입니다. [독립 기능 검사](../evals/tdd/README.md)와 기존 품질 비교를 구분합니다.
