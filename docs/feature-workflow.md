# 신규 기능·탐색·계획·버전 검토

검토일: 2026-10-20. 명령의 개수보다 각 기능이 서로 다른 판단을 돕는지가 기준입니다.

## 신규 기능 구현은 이미 지원한다

`sharp-frames-development`는 기능 추가·버그 수정·일반 리팩터링을 모두 담당합니다.
요구한 동작, 기존 구현과 호출부, 재사용 가능한 정책, 실패와 상태 변화, 검증과 최종 diff를
함께 확인합니다. 신규·수정 동작은 테스트를 먼저 실행해 관련 실패를 확인하고 구현하는
TDD 흐름이 기본이며, [케이스 관리와 사용자 흐름](testing-workflow.md)을 함께 다룹니다. 신규 기능 전용 `build`를 추가하면 같은 지침을 두 군데 관리하게 됩니다.

원하는 작업만 짧게 요청하면 됩니다.

```text
$sharp-frames-development 로그인과 게시글 CRUD API 만들어줘.

$sharp-frames-development 이 코드 정리해줘.
```

사용자가 조건을 모두 열거해야만 작동하는 스킬은 아닙니다. 관련 계약을 코드에서 찾고
중요한 미정 정책은 확인하되, 이미 정한 내용을 반복해서 묻지 않게 구성했습니다.
기존 코드 정리는 동작과 공개 계약을 유지하는 범위에서 진행합니다. 완전히 새로운
서비스라면 작은 기본 구성을 선택하고 구현·검증합니다. 꼭 지켜야 할 사업 규칙이나
배포 조건이 있다면 덧붙이면 됩니다. 재사용·책임 분리·테스트 절차를 매번 지시할 필요는 없습니다.
Claude Code에서는 `$sharp-frames-development` 대신 `/sharp-frames-development`로 호출합니다.

## 브레인스토밍과 플래닝은 조건부로 도움이 된다

| 상황 | 적합한 기능 | 그 단계가 줄이려는 문제 |
| --- | --- | --- |
| 어떤 문제를 해결할지·어느 방안이 맞는지 불명확 | `brainstorm` | 그럴듯하지만 필요 없는 기능을 구현하거나 임의 정책을 정하는 문제 |
| 목표는 정해졌지만 여러 모듈·데이터·배포가 얽힘 | `plan` | 재사용 지점 누락, 호출부 불일치, 작업 순서·검증·이전 경로 누락 |
| 요구와 수정 위치가 명확한 작은 기능 | `sharp-frames-development` | 별도 탐색·문서 없이 범위에 맞게 구현·검증 |

`brainstorm`은 사용자 문제·현재 흐름·대안을 비교해 추천 범위와 수용 기준을 만듭니다.
`plan`은 선택한 방안을 실제 코드와 대조해 재사용 지점, 변경 단위와 순서, 확인 방법으로
바꿉니다. 목표를 결정하는 일과 실행을 분해하는 일의 산출물이 달라 분리했습니다.

이는 품질을 자동 보장한다는 뜻은 아닙니다. 탐색을 길게 끌거나 현재 코드 없이 계획만
상세하게 쓰면 비용이 늘고 잘못된 확신을 줄 수 있습니다. 작은 변경에 의무 적용하지 않고,
필수 질문과 가정을 구분하며, 기존 구현·호출부를 근거로 삼고, 검증한 것과 예정인 것을
분리하도록 했습니다. 문서 생성·커밋·계획 승인을 자동 의식으로 만들지 않습니다.

```text
$sharp-frames-brainstorm 재주문 기능을 바로 결제하는 방식과 장바구니를 채우는 방식으로
비교해줘. 품절과 바뀐 가격을 사용자가 확인할 수 있어야 해. 아직 구현하지 마.

$sharp-frames-plan 장바구니 미리보기 방안으로 구현 계획만 세워줘.
기존 가격 계산과 소유권 검사를 활용하고, 변경할 계약·호출부·검증을 정리해줘.

$sharp-frames-development 이 계획대로 구현하고 검증해줘.
```

요구가 충분하고 구현까지 요청했다면 한 번에 진행할 수도 있습니다.

```text
$sharp-frames-development 주문 내역에서 재주문 미리보기를 추가해줘.
본인 주문만 조회하고 현재 가격으로 계산하며 품절 항목도 보여줘.
기존 모듈 활용과 변경 순서를 짧게 정리한 뒤 구현·검증까지 진행해줘.
```

별도의 탐색·계획 명령을 거쳐야만 구현이 가능하도록 잠그지 않습니다.

## 버전 검토는 독립 기능이 필요하다

리뷰는 특정 변경의 문제를, `gain`은 이미 한 개선의 전후 효과를 다룹니다. 어느 버전을
선택할지 판단하려면 현재 외부 자료와 호환성·지원 정책을 조사해야 하므로 둘만으로는
부족합니다. `sharp-frames-versions`가 이 판단을 담당합니다.

```text
$sharp-frames-versions 이 백엔드의 FastAPI·Pydantic 버전을 유지할지 올릴지 검토해줘.
공식 릴리스·이전 문서와 국내외 개발자의 실제 이슈를 찾아줘.
유지 / 같은 계열 업데이트 / 큰 버전 이전을 비교하고,
우리 코드의 필수 수정·선택적 활용·검증·배포 영향·예상 서비스 효과를 알려줘.
지금은 패키지를 바꾸지 마.
```

라이브러리별로 다음 내용을 받습니다.

| 판단에 필요한 내용 | 확인하는 근거 |
| --- | --- |
| 현재 상태와 후보 | 선언 범위·lock 해석·관측 설치·운영 배포를 구분하고 공식 버전·배포 날짜 확인 |
| 유지 비용과 업데이트 이유 | 지원 종료·적용되는 보안 공지·필요한 기능·운영 장애 등 실제 동기 |
| 버전별 변화 | 공식 릴리스·이전 안내·런타임·플러그인·전이 의존성 제약 |
| 개발자 경험 | 버전·환경·재현·유지관리자 답변·해결 버전이 있는 실제 이슈와 경험담 |
| 코드 수정 범위 | 사용 API·정책 소유자·호출부·설정·직렬화·테스트·배포에 적용되는 변화 |
| 개선 가능한 범위 | 호환을 위한 필수 수정과 새 기능의 선택적 활용을 구분 |
| 추천과 비용 | 유지·계열 내 갱신·단계적 이전 중 추천, 근거·위험·조사 공백·재검토 조건 |
| 도입 확인 | 계약·회귀·동일 조건 성능 검사, 데이터 변경과 롤백의 한계 |

최신 버전이 항상 최선이라는 전제도, 큰 버전 변경은 항상 피해야 한다는 전제도 두지
않습니다. 해당 서비스에 필요한 개선이 없고 현재 계열이 지원된다면 유지가 합리적일 수
있습니다. 반대로 적용되는 보안 결함이나 지원 종료가 있으면 기다리는 비용을 평가합니다.
정확한 판정은 매번 현재 자료와 실제 사용 코드를 조사한 뒤 내립니다.

커뮤니티 글은 공식 명세와 역할이 다릅니다. 특정 환경의 장애·이전 부담을 찾는 데
유용하지만 댓글 수를 장애율이나 합의로 바꾸지 않습니다. 한국어 자료도 관련성이 있을 때
찾되 없으면 없다고 밝힙니다. 문서의 성능 수치를 우리 서비스의 개선 수치로 제시하지
않으며, 현행 자료에 접근하지 못하면 최신성에 의존한 결론을 보류합니다.

검토 명령은 의존성을 바꾸지 않습니다. 변경을 요청하면 검토 결과를 바탕으로 실제 이전을
구현할 수 있습니다. 규모가 크면 `plan`을 활용하되, 단순 핀 갱신에 대형 계획을 강제하지
않습니다. 운영 데이터가 바뀌면 버전 핀을 되돌리는 것만으로 복구되지 않을 수 있습니다.

## 참고한 공개 사례와 채택 범위

[Superpowers brainstorming](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/brainstorming/SKILL.md)과
[writing-plans](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/writing-plans/SKILL.md)는
요구 탐색과 구현 계획을 별도로 제공합니다. 문제 이해와 작업 분해를 나누는 판단은
참고했습니다. 해당 패키지의 지정 문서 경로·다른 스킬 의존·절차를 그대로 이식하지 않고
Sharp Frames의 독립 실행과 작업 크기에 맞춰 새로 작성했습니다. 원문 복제는 없습니다.

[Renovate versioning](https://docs.renovatebot.com/modules/versioning/)은 버전 정렬·범위와
생태계별 번호 체계를 구분하고, 호환성 파괴가 큰 버전 번호에만 한정되지 않음을 설명합니다.
따라서 버전 숫자 대신 실제 변경 안내와 프로젝트 제약을 확인하도록 했습니다.
[release age 설정](https://docs.renovatebot.com/configuration-options/#minimumreleaseage)은
새 배포 후 관찰 기간을 표현하는 사례입니다. 기다린 날짜 자체를 안전성 증거로 삼지는 않습니다.

[Dependabot 설정](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference#cooldown)은
업데이트 정책과 보안 업데이트를 구분하는 운영 사례입니다. Sharp Frames는 해당 봇을
구현하거나 자동 갱신하지 않습니다. 봇이 제안한 후보도 우리 코드에서의 이익·수정 범위·
검증을 판단해야 한다는 것이 이 스킬의 역할입니다. 설정의 구체 기본값은 변할 수 있어
사용할 때 원문을 다시 확인합니다.

이 사례들은 설계의 참고 근거이며 새 명령의 생산성·품질 향상을 입증하지 않습니다.
[기능 검사와 한계](../evals/discovery/README.md)는 별도로 공개합니다.
