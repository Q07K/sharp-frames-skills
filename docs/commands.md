# Sharp Frames 사용 안내

명령 하나가 한 가지 목적을 수행합니다. 평소 기능 구현에는 기존 스킬을 쓰고,
리뷰·전체 진단·부채 정리·효과 비교는 필요할 때 골라 실행합니다.

| 호출 | 역할 | 소스 수정 |
| --- | --- | --- |
| `$maintainable-development` | 기능 구현·버그 수정·일반 리팩터링 | 요청 범위 내 수정 |
| `$sharp-frames-brainstorm` | 기능 목표·대안·범위·수용 기준 구체화 | 읽기·보고 |
| `$sharp-frames-plan` | 재사용·변경 순서·검증·마이그레이션 계획 | 읽기·보고 |
| `$sharp-frames-versions` | 최신 공식·커뮤니티 근거로 버전 유지·업데이트 영향 판단 | 읽기·보고 |
| `$sharp-frames-review` | 변경 diff·커밋·브랜치·PR 리뷰 | 읽기·보고 |
| `$sharp-frames-audit` | 프로젝트 전체·하위 시스템 진단과 우선순위 | 읽기·보고 |
| `$sharp-frames-debt` | 신규·기존·해소·미확인 기술 부채 정리 | 읽기·보고 |
| `$sharp-frames-gain` | 개선 전후 효과·근거·비용·남은 위험 비교 | 읽기·보고 |
| `$sharp-frames-map` | 프로젝트 흐름·정책 소유자·재사용 후보 파악 | 읽기·보고 |
| `$sharp-frames-improve` | 선택한 지적·개선 항목 적용과 검증·효과 정리 | 요청 범위 내 수정 |
| `$sharp-frames-help` | 명령 목록·선택 기준·사용 예시 | 읽기·보고 |

표의 ‘읽기·보고’는 구현 소스·Git 인덱스·브랜치를 수정하지 않는다는 뜻입니다.
사용자가 보고서나 부채 대장의 저장을 요청하면 해당 문서만 저장할 수 있습니다.
검사 도구가 만드는 임시 파일은 구분하며, 운영 DB·외부 서비스에 대한 실행은 별개입니다.

## 어떤 명령을 고를까

| 질문 | 선택 | 받는 결과 |
| --- | --- | --- |
| 어떤 문제를 어떤 기능으로 풀까 | `brainstorm` | 목표·대안·추천·최소 범위·수용 기준 |
| 여러 모듈을 어떤 순서로 바꿀까 | `plan` | 기존 모듈 재사용·작업 순서·검증·이전 계획 |
| 라이브러리 버전을 유지할까 올릴까 | `versions` | 현재 근거·개발자 경험·호환성·수정 범위·서비스 효과 |
| 요구가 정해진 신규 기능을 만들어 달라 | `maintainable-development` | 요청 기능 구현·기존 기능 재사용·회귀 검증 |
| 어디에 무슨 코드가 있고 재사용할 것은 무엇인가 | `map` | 흐름·정책 소유자·호출부·검증 위치·모르는 부분 |
| 이 변경이 문제를 만들었는가 | `review` | 특정 diff의 구체적 지적, 재현 조건, 영향, 수정 방향 |
| 프로젝트 전체에서 무엇을 먼저 고칠까 | `audit` | 시스템 지도, 조사 깊이, 근거 있는 문제와 우선순위 |
| 리뷰 지적을 실제로 고쳐 달라 | `improve` | 선택 범위 수정, 회귀 검증, 남은 부채·효과 |
| 이번 변경이 무엇을 미뤘고 무엇을 갚았나 | `debt` | 신규·증가·기존·해소·부분 해소·출처 미확인 구분 |
| 고친 뒤 무엇이 좋아졌고 무엇이 더 드나 | `gain` | 관찰·측정·예상 효과, 동일 조건 비교, 비용·한계 |

## 사용 예시

```text
$sharp-frames-help
$sharp-frames-map 주문 처리 흐름과 재사용 가능한 가격 계산 코드를 찾아줘.
$maintainable-development 기존 계산을 활용해 견적 API를 만들어줘.
$sharp-frames-review 현재 커밋하지 않은 변경을 리뷰해줘.
$sharp-frames-improve 리뷰 1번을 수정하고 회귀 검증까지 해줘.
$sharp-frames-debt main부터 현재 변경까지 신규·해소·남은 부채를 정리해줘.
$sharp-frames-gain 이번 개선의 실제 효과와 예상 효과, 새로 생긴 비용을 알려줘.
$sharp-frames-audit 이 백엔드 전체를 검토하되, 깊게 읽은 범위와 미검토 범위를 표시해줘.
```

이 순서를 매번 전부 실행할 필요는 없습니다. `review`에서 문제를 찾았다고 자동 수정하지
않으며, `improve`를 요청하면 승인된 범위의 일반적인 구현을 진행합니다.
이미 명시한 수정 요청에 대해 형식적인 계획 승인을 반복하지 않습니다.

신규 기능의 크기별 선택과 버전 검토의 출력은 [기능 개발 흐름](feature-workflow.md)에 정리합니다.

## 기술 부채를 다루는 기준

변경 비교에는 기준 리비전이 필요합니다. 기준이 없으면 발견한 부채를 ‘새로 생김’으로
단정하지 않습니다. `TODO`·`shortcut` 검색은 후보 수집이며 실제 코드와 기존 대장을 확인합니다.
주석 삭제·파일 이동은 해소 증거가 아닙니다. 동작 변경과 검증이 확인되어야 해소로 분류합니다.

의도적인 제한에는 이유·영향·다시 볼 조건을 남깁니다. 소유자·기한은 근거가 있을 때만
기록하고, 활성 오류나 권한 문제는 ‘나중에 갚을 부채’로 감추지 않습니다.
기존 대장이 있으면 ID와 이력을 유지합니다. 대장 파일을 만드는 것은 자동 기본 동작이 아닙니다.

## 효과를 보여주는 기준

| 표현 | 필요한 근거 |
| --- | --- |
| 중복 가격 정책이 한 곳으로 모였다 | 전후 소스와 실제 호출부 |
| 조회가 10회에서 6회로 줄었다 | 같은 데이터·시나리오·측정 방식의 실행 기록 |
| 리뷰가 쉬워질 것으로 예상된다 | 구조 변화의 이유와 검증할 방법; 측정 시간으로 포장하지 않음 |
| 스킬 때문에 품질이 높아졌다 | 스킬 사용·미사용을 통제한 별도 비교 실험 |

단위·환경·작업량·측정 방식이 다르면 비교를 막거나 필요한 정규화를 별도로 검증합니다.
기준값 0의 변화율은 정의할 수 없고, 기준이 없는 효과는 ‘미측정’입니다.
`gain`의 숫자 도구는 제공된 관찰값의 비교 가능성과 산술을 확인하며 실제 측정 여부를 인증하지 않습니다.

## 지원 범위

각 스킬 폴더는 단독 실행에 필요한 지침·참고 자료·도구를 포함합니다. `help`의 목록은
배포 패키지 목록이며 로컬에 전부 설치되어 있다는 증거는 아닙니다. 현재 문서의 직접
호출 표기는 `$skill-name`입니다. 다른 호스트의 슬래시 메뉴·플러그인 네임스페이스는
실제 설치 방식에 따라 달라집니다.

현재 패키지는 전역 모드 전환, 상시 주입 훅, 비용 상태 패널, 세션 기록 수집을 구현하지 않습니다.
원칙과 작업 기능의 명시적 호출을 우선 제공합니다. [비교 조사와 반영 기준](skill-landscape.md)을 참고하세요.
